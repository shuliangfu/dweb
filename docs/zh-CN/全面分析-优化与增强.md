> dweb 已是 **功能面很完整** 的 Deno/Bun 全栈框架（多引擎 × 多渲染模式 × CLI ×

> Islands**）；\

> 6）**多应用 Console 命令面**（`dweb-cli run` 文件路由；单应用不沾边）；\

## 1. 框架定位与边界

### 1.1 定位

**类 Next/Remix 心智的全栈 Web 框架**，面向 Deno 与 Bun：

- 把 **HTTP
  服务、文件路由、多模式渲染、客户端构建/HMR、Session、插件、中间件、可选实时通道、CLI
  脚手架** 收成一条产品线。
- 视图层 **可插拔**：推荐 **`@dreamer/view`**，兼容 **Preact / React**。
- 数据约定：**路由 `load(ctx)`** 服务端取数；CSR/Hybrid 经
  **`/_dweb_data`（或文档中的 data 路径）** 与 SSR 同源，减少「手写 API
  拉首屏数据」。

### 1.2 刻意边界（不宜塞进 dweb 核心）

| 不宜进核心                    | 原因                    |
| ----------------------------- | ----------------------- |
| 业务组件库 / 设计系统         | 属于 `ui-view` 或业务仓 |
| 完整 CMS / 后台模板           | 示例即可                |
| 重写 view/preact/react 运行时 | 在对应包优化            |
| 默认强制微服务编排            | 配置 + 插件扩展即可     |
| **Islands / 分区水合**        | **产品否决**，见 §1.4   |

### 1.3 与 monorepo 其它包关系

```text
dweb（编排 / 产品线）
  ├── @dreamer/server · router · render · esbuild · session · middleware(s)
  ├── @dreamer/runtime-adapter（fs/path/env/process…）
  ├── @dreamer/view | preact | react（视图引擎，轻量整页渲染/水合）
  ├── @dreamer/test（describe/it/expect/mock/浏览器；挂宿主 Deno.test / bun:test）
  ├── @dreamer/console（CLI 工具库；用户 Console App 规划见专文）
  ├── @dreamer/plugin · plugins · lifecycle · service · database · …
  └── CLI（含 test launcher）/ init 模板 / examples 矩阵
```

**优化原则**：dweb 做 **编排与默认体验**；重逻辑下沉到专项包；避免在 dweb 复制
view 的 DOM 运行时，也 **避免在 dweb 复制一套测试执行引擎**（执行权留给宿主 +
`@dreamer/test` 适配层）。

### 1.4 明确不做：Islands / 部分水合

| 维度           | 结论                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| **产品决策**   | **不做** Islands、不规划分区水合、不为「岛屿边界」引入新写法                                                  |
| **用户体验**   | Islands 拆分心智（哪些是岛、props 序列化边界、交互边界）**写代码不习惯**，学习成本高、排错难                  |
| **引擎定位**   | **view / Preact 本身已是轻量级** 运行时；整页 CSR/SSR/Hybrid 水合在典型 dweb 应用体量下足够                   |
| **性能路径**   | 优先 **包体（子路径/拆 chunk）**、**流式 SSR**、**`load` 数据契约与缓存**、**HMR/构建可维护**，而非改交互模型 |
| **与旧文关系** | [OPTIMIZATION_ANALYSIS](./OPTIMIZATION_ANALYSIS.md) 若仍写 islands，以 **本文否决** 为准                      |

**Hybrid 默认形态保持**：服务端 HTML + **整页客户端激活**；水合失败用 view 2.1
`mismatchMode`（`continue` / `assert` / `remount`）等 **配置透传**
即可，不引入岛屿 API。

## 2. 架构速览（以源码为准）

```text
┌─────────────────────────────────────────────────────────────────┐
│ CLI：init / dev / build / start / preview / test / generate / … │
│      test = 产品层 launcher（spawn 宿主 test；见 §7.4）          │
├─────────────────────────────────────────────────────────────────┤
│ core/                                                           │
│   App（生命周期 · 中间件装配 · 插件 · 启停）                      │
│   config · service · middleware · plugin · database · lifecycle │
│   app-http-middlewares（框架 HTTP 默认栈）                        │
├─────────────────────────────────────────────────────────────────┤
│ feature/                                                        │
│   router · render-{ssr,csr,ssg,hybrid} · build                  │
│   csr-client-builder + chunk + middleware + route-manifest      │
│   load-data · load-route-module · module-cache · strip-load     │
│   socket-io · websocket · server · command                      │
├─────────────────────────────────────────────────────────────────┤
│ utils/：path · security · errors · i18n · runtime · test-launcher · version │
└─────────────────────────────────────────────────────────────────┘
```

| 层级        | 关键路径                        | 行数量级    | 职责                                                          |
| ----------- | ------------------------------- | ----------- | ------------------------------------------------------------- |
| 应用内核    | `core/app.ts`                   | ~1.5k       | 启动/关闭、装配渲染与客户端脚本、信号                         |
| 配置        | `core/config.ts`                | ~0.9k       | 深度合并、校验、目录推断                                      |
| HTTP 默认栈 | `core/app-http-middlewares.ts`  | ~0.1k       | security / 可选 cors·限流·压缩 / requestId / session / health |
| 客户端构建  | `feature/csr-client-builder.ts` | **~2.4k**   | esbuild、HMR、多引擎入口、Windows 兼容                        |
| Chunk 契约  | `feature/csr-client-chunk.ts`   | ~0.3k       | 索引/匹配/HMR 映射（已从 builder 拆出）                       |
| 渲染        | `feature/render-*.ts`           | 各 0.3–0.5k | SSR/CSR/SSG/Hybrid HTML 与挂载                                |
| 数据        | `load-data-middleware`          | ~0.3k       | `load()` 与 data 端点                                         |
| 实时        | `socket-io.ts` / `websocket.ts` | ~0.2k       | 挂同一 HTTP 服务                                              |

### 2.1 公共导出

`deno.json` / `package.json` 已提供：

- 主入口 `.` → `App`、类型、部分再导出
- `./core/*`：app、config、service、middleware、plugin、lifecycle、database
- `./feature/*`：server、router、render、build、command、socket-io、websocket
- `./cli`、`./setup`、`./types`

**评价**：子路径方向正确；业务仍多从主入口拿 `App`，tree-shake 收益有限，但
**库内模块边界清晰**，利于维护。

### 2.2 渲染模式矩阵（产品核心资产）

| 模式            | 含义                     | 典型场景      |
| --------------- | ------------------------ | ------------- |
| **CSR**         | 服务端出壳 + 客户端挂载  | SPA、后台     |
| **SSR**         | 每请求服务端渲染 HTML    | SEO、首屏     |
| **SSG**         | 构建期静态 HTML          | 文档、营销站  |
| **Hybrid**      | 服务端 HTML + 客户端激活 | 内容站 + 交互 |
| **Hybrid-flat** | 扁平路由变体             | 特定目录结构  |

× 引擎：**view / preact / react** × examples **basic/advanced** →
测试与文档矩阵巨大，**是护城河也是维护成本**。

## 3. 已经做得好的部分（边际收益递减）

1. **多引擎 × 多模式矩阵完整**，examples 覆盖面大，适合当「规范用法」。
2. **文件路由 + `load()` 数据契约** 心智清晰（CSR/Hybrid 不必为每个页面手写
   REST）。
3. **`runtime-adapter`** 统一 fs/path/env，Deno+Bun 双跑路径成熟。
4. **开发体验**：HMR、chunk 名匹配历史兼容、`module-cache` LRU、dev
   缓存策略细致。
5. **安全与生产底座（3.5.11 已增强）**：
   - 安全头中间件
   - **opt-in** `cors` / `compression` / `rateLimit`（`@dreamer/middlewares`）
   - `serializeJsonForInlineScript`、sanitize、错误码体系
   - `PRODUCTION_CHECKLIST`
6. **构建工程债已开始还**：`csr-client-chunk` 拆出 +
   单元覆盖；`app-http-middlewares` 从 `app.ts` 委托。
7. **CI**：Linux/macOS/Windows Deno；Bun job 保留 unit/integration，**浏览器 e2e
   暂注释**（稳定性权衡，见 §7）。
8. **热路径小优化**：escape / inline JSON 无特殊字符快路径；hash 资产
   `immutable` 缓存头。

**总判**：功能与产品形态 **「能用且够全」**；主战场是
**质量上限、构建复杂度、依赖新鲜度、测试文档真实性**。

## 4. 还能优化什么？（性能 / 工程 / 成本）

### 4.1 依赖与版本（P0，立刻可做）

| 现状                       | 问题                                                                                       | 建议                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `@dreamer/view@^2.0.5`     | **吃不到 2.1.0**：细粒度 `/csr` `/reactivity`、水合 `mismatchMode`、For LIS、安全 props 等 | 升 **`^2.1.0`**；examples/init 模板/`jsr-versions` 同步        |
| 其它 `@dreamer/*` **声明** | 与 monorepo 本地 **数字大多已齐**                                                          | 见 **[依赖分析-优化与升级.md](./依赖分析-优化与升级.md)**      |
| 子包 **传递 imports**      | 多包仍 pin `runtime-adapter@^1.0.x`、render 仍 `view@^2.0.2`                               | 浪潮 0：底座批量对齐，勿只改 dweb caret                        |
| 客户端构建注释             | builder 内仍写「避免 `@dreamer/view/csr`」                                                 | **2.1 后应重新评估**：主包 vs `/csr` 对 esbuild 图与包体的影响 |

**配套验证**：view 引擎 unit + integration +（至少）view-hybrid / view-csr e2e
冒烟。\
**专项文档**：依赖分层、逐包缺口、发版顺序 →
[依赖分析-优化与升级.md](./依赖分析-优化与升级.md)。

### 4.2 客户端构建链路（P0，工程债主杠杆）

**问题**

- `csr-client-builder.ts` 仍 **~2.4k 行**：入口生成、esbuild
  配置、多引擎分支、Windows 路径、历史 chunk 命名兼容揉在一起。
- chunk 已拆 `csr-client-chunk.ts`，但 **HMR / esbuild-options /
  entry-generators** 仍可再拆。
- 兼容「猜文件名」分支多 → 改一处易回归。

**优化方向（不改 CLI 对外契约）**

| 步骤            | 内容                                                                      | 收益                |
| --------------- | ------------------------------------------------------------------------- | ------------------- |
| 继续拆文件      | `hmr.ts`、`esbuild-options.ts`、`entry-generators/{view,preact,react}.ts` | 可测、可审          |
| Golden 契约     | 多段 path、根 index、layout → chunk 索引结果快照                          | 防回归              |
| 统一 naming     | 评估收敛 `entryNames`/`chunkNames`，少「猜名」                            | 降复杂度            |
| 可观测          | dev 可选日志：`请求 path → chunk 文件`                                    | 排障                |
| view 2.1 子路径 | 试验 `external` + 从 `/jsx-runtime`、`/csr` 解析                          | 潜在包体/解析清晰度 |

### 4.3 服务端渲染与数据路径（P1）

| 项          | 现状                             | 优化                                                                              |
| ----------- | -------------------------------- | --------------------------------------------------------------------------------- |
| SSR 响应    | 多为整页字符串一次返回           | 对齐 view **`renderToStream` / render 包流式**；可选配置开启                      |
| Hybrid 同构 | 服务端路径与客户端路由可能双实现 | 深化 **view `createRouter({ url, ssr })` / `renderRouterToString`**               |
| 水合失败    | 依赖引擎默认                     | view 2.1：`mismatchMode: remount \| assert \| continue`；dweb **配置透传** + 文档 |
| 水合范围    | **整页 hydrate**（产品默认）     | **保持**；不引入 Islands（§1.4）                                                  |
| `load()`    | 每请求可打                       | 可选 **短缓存**（path+query，dev 关）；文档写清失效策略                           |
| SSG         | 构建期静态                       | 长期 **ISR/revalidate**（路由 TTL / webhook）——产品级，非必做                     |
| 首屏数据    | 巨型 inline `__data` 可能拖 HTML | 阈值阈值外置 `/_dweb_data`；文档「何时 inline / 何时请求」                        |

### 4.4 生产传输与缓存（P1，部分已落地）

| 项             | 现状（3.5.11）                           | 下一步                                                               |
| -------------- | ---------------------------------------- | -------------------------------------------------------------------- |
| 压缩           | **opt-in** `compression`                 | 文档强化「生产推荐开」；压测 brotli/gzip 默认档                      |
| CORS / 限流    | **opt-in**                               | 模板注释 + PRODUCTION_CHECKLIST 已有；可增加 `init` 生产预设 profile |
| 静态 hash 资产 | `HASHED_ASSET_CACHE_CONTROL` + immutable | 扩展到 CSS/字体/图片流水线一致性                                     |
| HTML 文档缓存  | 常 no-store/短缓存                       | 保持；与 CDN 指南对齐                                                |

### 4.5 `App` / 配置体量（P1 工程）

| 问题                | 建议                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------- |
| `app.ts` ~1475 行   | 继续拆：`app-client-script.ts`、`app-signals.ts`、`app-render-init.ts`（中间件已拆）  |
| `config.ts` ~900 行 | schema 分段：server / render / router / security / socket；校验函数单测已多可再补边界 |
| 配置键膨胀          | 新能力默认 **opt-in**；避免无文档键                                                   |

### 4.6 运行时与热路径微优化（P2）

- 模块缓存命中率与 LRU 参数可配置化（大项目）。
- 路由模块加载：减少重复 `import` 解析（已有 cache-bust 策略，可做 metrics）。
- 错误页 / inline `__data`：已有 escape 快路径；大 payload 可考虑外置 data
  请求而非巨型 inline。
- 避免在请求路径上同步读大配置文件（启动期缓存）。

### 4.7 包体与导入图（P2）

- 主入口 `App` 会拉较重依赖图 → 文档推荐：**仅 CLI/服务入口 import
  dweb**；库代码用 `./feature/*` 子路径。
- 评估 publish `exports` 是否需 **`sideEffects`** 声明（若适用）。
- examples 构建产物是否应 gitignore 更干净（减仓膨胀，非运行时）。
- **轻量引擎红利**：view/Preact 体积本就小 → 优化重点是 **entry
  生成质量、按路由拆 chunk、避免误打服务端-only 代码进客户端**，不是改水合模型。

### 4.8 多应用 / 项目布局与配置加载（P1 工程）

| 项           | 现状                                        | 优化                                                                       |
| ------------ | ------------------------------------------- | -------------------------------------------------------------------------- |
| 单 vs 多应用 | init 已分支；路径 `useSrc` 决定 `src/` 前缀 | 文档与错误信息统一「单应用纯 Web / 多应用才有 console」                    |
| common 配置  | 多应用可共享                                | 校验边界：common 不宜塞某 app 专有 server 端口等                           |
| 配置体膨胀   | `config.ts` 大                              | 分型文档：`WebConfig` vs 规划中的 `ConsoleConfig`（无 server/render 必填） |
| 静态资源扫描 | 多应用构建                                  | 明确 **排除 console 应用目录**（规划见 Console 专文）                      |

### 4.9 CLI / 开发路径热路径（P2）

- `dev` 冷启动：配置加载、路由扫描、首次 esbuild 可分别打耗时日志（opt-in）。
- 路由表变更时增量重建 chunk 索引（已有能力则文档化；缺口则列债）。
- Windows 路径分支集中测（builder 历史痛点），避免「只在 mac 绿」。

## 5. 还能增强什么？（产品能力）

下列为 **增强/扩展**，与「变快」不同；按用户价值排序。\
**渲染侧增强不包含 Islands**（§1.4）；前端体验靠轻量引擎 + 整页模式 +
构建/数据路径。

### 5.1 安全与合规（高价值）

| 能力                  | 现状          | 增强建议                                                                       |
| --------------------- | ------------- | ------------------------------------------------------------------------------ |
| CORS / 压缩 / 限流    | 3.5.11 opt-in | **生产 profile**：`dweb init --preset production` 写入推荐组合                 |

#### 7.4.1 分析结论（职责与能不能）

| 问题 | 答案 |
| ---- | ---- |
| **能不能用 `@dreamer/test`？** | **能，而且已是正确分层的一半**：用例 API + 浏览器/Mock **已在** `@dreamer/test`；dweb 与 monorepo 测试已依赖它。 |
| **`@dreamer/test` 能否单独替代 `deno test` / `bun test`？** | **不能**。它是 **适配库**（`describe`/`it` → **`Deno.test` 或 `bun:test`**），**没有** 文件发现、并行调度、原生报告、覆盖率 CLI。包内 **无** `bin` / `cli` 导出。 |
| **「集成 @dreamer/test」正确含义？** | 集成的是 **测试体验产品面**（CLI 入口 + 项目约定 + 可选策略），**不是**把 test 包装进进程当唯一执行器。用例层早已集成；缺口曾在 **launcher 产品化**（现 L1 已补）。 |
| **推荐架构？** | **① 产品 launcher（dweb-cli）+ ② 宿主执行器（Deno/Bun test）+ ③ 用例框架（@dreamer/test）**。用户只面对 `dweb-cli test`；底层 **仍 spawn 宿主**。**不要**自研第三套 runner（方案 C）。 |
| **用户能否完全不敲 deno/bun test？** | **入口层可以**（推荐只记 `dweb-cli test`）；**进程层不行**——子进程仍是宿主 test。框架仓自测可继续直调宿主。 |
| **Node 呢？** | **今天不可用**。`getRuntime()` 仅 `deno \| bun`；`@dreamer/test` 无 `node:test`；RA 对 Node 仍拒绝。属 [Node兼容工程量分析](./Node兼容工程量分析.md) **M7**，非 dweb 单包包装能完。 |

#### 7.4.2 三层职责（必须分清）

```text
┌──────────────────────────────────────────────────────────────┐
│  ① 产品入口（dweb）— L1 已实现                                 │
│     dweb-cli test [paths…] [--unit|--e2e] [--filter] …        │
│     · 解析项目、选 runtime、拼宿主参数、失败 exit(code)         │
│     · L2 预留：Bun e2e skip/串行、pw 未装提示等策略            │
│     · 报告预留（§7.4.10）：JUnit 透传 + 产品 json/html/md     │
└────────────────────────────┬─────────────────────────────────┘
                             │ spawn
┌────────────────────────────▼─────────────────────────────────┐
│  ② 宿主执行器（运行时自带）                                    │
│     Deno: deno test -A …   Bun: bun test …                   │
│     · 文件发现 · 并行 · 宿主 reporter · --coverage / filter  │
│     · Deno: pretty|dot|junit|tap；Bun: console|dots|junit     │
│     · **无** 原生「用例结果 → JSON/HTML/Markdown」一等支持   │
└────────────────────────────┬─────────────────────────────────┘
                             │ load *.test.ts
┌────────────────────────────▼─────────────────────────────────┐
│  ③ 用例框架（@dreamer/test）— 早已存在，CLI 不 import 执行它     │
│     describe / it / expect / mock / hooks / browser          │
│     · Deno → Deno.test · Bun → bun:test · 无独立 CLI           │
└──────────────────────────────────────────────────────────────┘
```

**类比**：Jest 既写用例又跑；dreamer 更接近 **「Vitest/Jest API 风格库 +
宿主 runner」**。`dweb-cli test` ≈ 脚手架统一入口（如 `next` 侧测试入口心智），
**不是**第三套引擎。

#### 7.4.3 代码锚点（以仓库源码为准，L1）

| 组件 | 路径 | 行为摘要 |
| ---- | ---- | -------- |
| CLI 注册 | `src/cli.ts` | `test` + `-a/--app`、`--unit`、`--integration`、`--e2e`、`-f/--filter`、`--coverage`、`--runtime`、`--verbose` |
| 实现 | `src/cmd/test.ts` | 解析选项 → task 或 `getTestArgs` → `createCommand` spawn；失败 **`exit(code)`** |
| 路径 / task 策略 | `src/utils/test-launcher.ts` | `resolveTestPaths`、`shouldPreferTestTask`、`parseTestRuntime`、`splitAppAndPaths` |
| 宿主参数 | `src/utils/runtime.ts` → `getTestArgs` | paths + filter + coverage；Deno：`test -A … --filter=… --coverage=…`；Bun：`test … -t … --coverage` |
| 运行时闸门 | `getRuntime()` / `--runtime` | **仅** `deno` \| `bun`；非法 runtime 报错 |
| 用例框架 | monorepo `test/` → `@dreamer/test@^1.1.10` | 适配层；**CLI 不 import 它来跑用例** |
| dweb 依赖 | `deno.json` imports | 已有 `@dreamer/test@^1.1.10`（本仓自测） |
| init 模板 | `cmd/init/templates/*`、`generate.ts` | imports/依赖写入 `@dreamer/test`；`tests/unit/example.test.ts`；Bun `scripts.test = "dweb-cli test"`；**不**在 `deno.json tasks` 写 `dweb-cli test`（避免 task 与 CLI 递归） |
| 单测 | `tests/unit/test-launcher.test.ts`、`runtime.test.ts` 等 | launcher 纯逻辑 + `getTestArgs` 映射 |
| 本仓脚本 | `deno.json` tasks / `package.json` | 框架自测 **仍**可直写宿主命令（与用户入口双轨） |

**`shouldPreferTestTask` 规则（实现语义）**

- **走 task**（`tasks.test` / `test:<app>`）：仅当用户 **未** 指定自定义路径、分层、
  `--filter`、`--coverage`（默认路径即 `tests` 且无产品 flag）——兼容旧项目自定义脚本。
- **走宿主 `getTestArgs`**：有路径 / 分层 / filter / coverage 时 **一律** 直 spawn，
  保证 flag 语义不被 task 吞掉。
- 多应用指定 `-a` 且无 `test:<app>` task：提示后 **回退** 宿主测默认路径（不再硬失败）。

#### 7.4.4 方案对比（分析决策，不变）

| 方案 | 做法 | 优点 | 缺点 | 建议 / 状态 |
| ---- | ---- | ---- | ---- | ----------- |
| **A. 强化 launcher** | 路径/分层/filter/coverage/runtime 透传；默认 `tests`；task 条件优先 | 改动可控；复用宿主；兼容矩阵 | 底层仍是宿主 test | **已选；L1 ✅** |
| **B. launcher + 策略包** | A + e2e 串行、Bun skip、pw 引导、多应用 tests 路径细化 | 产品差异化；CI/本地同源 | CLI 变复杂 | **L2 待做** |
| **B′. launcher + 报告** | A + 宿主 reporter 透传 + 产品层汇总为 json/html/md（§7.4.10） | CI 与人读报告；仍不自研 runner | 需解析/模板；宿主差异 | **L1.5 / L2 待做**（已记需求） |
| **C. 自研 runner** | test 包自 discover/执行，绕过宿主 | 「一个引擎」幻想 | 成本/风险巨大 | **默认不做** |
| **D. `runTests()` API** | test 包编程式入口供 CLI import | 边界清晰 | 价值有限若仍 spawn | **可选 L3** |
| **E. Node 三引擎** | `node:test` 适配 + CLI | 三运行时一命令 | 跨 RA/test/CI | **P2+ / Node M7** |

#### 7.4.7 风险与边界

| 风险 | 缓解 |
| ---- | ---- |

| 报告与 `TEST_REPORT.md` 混为一谈 | 7.3 两类报告；机读产物默认进 `reports/` 或用户指定，不强制覆写 docs |

#### 7.4.10 测试报告需求（JSON / HTML / Markdown）— **仅规划，实现后置**

> **产品诉求（2026-07-22 记入）**\
> 用户希望 `dweb-cli test` **跑完后**能直接得到结构化/可读报告：至少 **JSON、
> HTML、Markdown**；并与 CI 常用 **JUnit**、覆盖率 **HTML/LCOV** 对齐。\
> **当前状态**：**未实现**。L1 仅 `stdout/stderr` 继承宿主 pretty 输出 +
> 可选 `--coverage` 原始收集；**无** `--report` / `--reporter` 产品 flag。

##### 现状（宿主能力 vs 产品能力）

| 产物类型 | `dweb-cli test` L1 | Deno 宿主（手写命令） | Bun 宿主（手写命令） |
| -------- | ------------------ | --------------------- | -------------------- |
| 终端 pretty / dots | ✅ 透传终端 | `--reporter pretty\|dot` | 默认 console / `--dots` |
| **用例结果 JSON** | ❌ | **无**原生 json reporter | **无**原生 json reporter |
| **用例结果 HTML** | ❌ | **无**原生 HTML test report | **无** |
| **用例结果 Markdown** | ❌ | **无** | **无** |
| JUnit XML | ❌ 未透传 | `--reporter junit` / `--junit-path` | `--reporter junit` + `--reporter-outfile` |
| TAP | ❌ 未透传 | `--reporter tap` | 视版本；**勿假设与 Deno 对等** |
| 覆盖率原始数据 | ✅ `--coverage` | `--coverage[=DIR]` | `--coverage` |
| 覆盖率 HTML / LCOV | ❌ 未封装后处理 | `deno coverage --html` / `--lcov` | `--coverage-reporter=text\|lcov` 等 |

##### 推荐实现路径（仍坚持方案 A：launcher，不自研 runner）

1. **L1.5-a — 宿主 reporter 透传（低成本，CI 优先）**
   - 产品 flag 草案：`--reporter junit|tap|dot`、`--report-out <path>`（或
     `--junit-path` 别名）。
   - 映射：Deno → `--reporter=…` / `--junit-path=…`；Bun → `--reporter=junit` +
     `--reporter-outfile=…`；**不支持的组合显式失败**，勿静默忽略。
2. **L1.5-b — 产品层统一摘要 → JSON / Markdown / HTML（中成本）**
   - 跑测时让宿主落 **JUnit（优先）或 TAP** 到临时/指定文件（结构化、可解析）。
   - CLI 解析为统一 `TestRunSummary`（总数 / 通过 / 失败 / skip / 时长 / 按文件
     或分层 unit|integration|e2e）。
   - 再写出：`test-report.json`、`test-report.md`、`test-report.html`（简单模板
     即可，本地可打开）。
   - 产品 flag 草案：`--report json,md,html`、`--report-dir reports/`（可逗号多
     格式）。
   - **禁止**以解析 pretty 终端彩色输出作为主路径（脆弱、宿主升级即碎）。
3. **L1.5-c — 覆盖率报告后处理（与「用例结果报告」分线）**
   - 产品 flag 草案：`--coverage-report html|lcov|text`。
   - Deno：`deno coverage <dir> --html` / `--lcov --output=…`。
   - Bun：对齐 `--coverage-reporter` / `--coverage-dir`（以当时 Bun CLI 为准）。
   - 覆盖率 HTML **≠** 用例结果 HTML；文档与 flag 命名须区分。

##### 与 `TEST_REPORT.md` 的边界

| | `docs/**/TEST_REPORT.md` | `dweb-cli test --report …`（规划） |
| - | ------------------------- | ---------------------------------- |
| 谁写 | 发版 checklist 人工/半自动维护 | 每次跑测 CLI 生成 |
| 受众 | 框架维护者、发版说明 | 应用开发者、CI、PR 评论 |
| 是否覆盖用例明细 | 分层统计与说明为主 | 可含当次 run 的 suite/case 摘要 |
| 默认路径 | 文档仓 `docs/` | 建议 `reports/` 或用户指定，**勿**默认覆写 docs |

框架发版仍刷新 **TEST_REPORT.md**；应用侧默认用 **机读/人读运行时报告**。二者可
并存，不互相替代。

##### 实现时涉及文件（预估，未改代码）

| 面 | 可能触点 |
| -- | -------- |
| CLI 选项 | `src/cli.ts`、`src/locales/*.json` |
| launcher | `src/cmd/test.ts`（spawn 后 / 并行写报告；注意 exit code 仍跟宿主） |
| 参数映射 | `src/utils/runtime.ts` → `getTestArgs` 或并列 `getTestReportArgs` |
| 纯逻辑 / 单测 | `src/utils/test-launcher.ts` 或新建 `test-report.ts`；unit 测映射与 summary |
| 模板 | 内嵌极简 HTML/MD 模板即可；避免重依赖 |

##### 验收草案（实现时再勾）

- [ ] `dweb-cli test --reporter junit --report-out …` Deno/Bun 至少一条绿路径
- [ ] `dweb-cli test --report json,md` 产出文件，summary 字段稳定、失败时 exit ≠ 0
- [ ] `--report html` 可本地打开；无需额外服务
- [ ] `--coverage-report html`（或文档化的两步命令）在 Deno 可用；Bun 限制写清
- [ ] 不支持的宿主/格式：**显式错误**，不静默降级为「只有终端」
- [ ] 文档：README CLI 表 + 本节状态从「规划」改为「已实现」+ CHANGELOG

##### 优先级建议（后续优化时）

| 顺序 | 项 | 理由 |
| ---- | -- | ---- |
| 1 | JUnit / TAP 透传 | CI 立刻可用，改动小 |
| 2 | `--report json,md` | 产品差异化；PR/发版可读 |
| 3 | `--report html` | 与 md 同源数据，模板即可 |
| 4 | `--coverage-report html\|lcov` | 覆盖率线独立，勿与用例报告绑死 |

**本迭代**：需求仅写入本文；**不实现代码**。排期归 **P1 / L1.5**（可与 L2 e2e
策略并行或先后，视人力）。

## 9. 成功标准（阶段性）

优化/增强「算见效」时至少满足：

1. **依赖**：view ≥ 2.1；view 引擎 hybrid/csr 回归绿。
2. **构建**：chunk/HMR 变更有 golden；builder 行数或模块边界可读性明显改善。
3. **生产**：新项目可按 PRODUCTION_CHECKLIST 一键理解
   cors/压缩/限流；无「默认裸奔」误解。
4. **文档**：TEST_REPORT 与发版版本一致；中文分析（本文）与 OPTIMIZATION **在
   Islands 等否决项上一致**（以本文为准）。
5. **性能（可选量化）**：选定 hybrid 示例首页 TTFB / JS
   体积基线，升级后不回退（**整页**模型下的包体/流式，非岛屿覆盖率）。
6. **Console（若启动实现）**：多应用可 `run` 自定义命令；单应用 init 流程 **零**
   console 提问。
7. **测试入口（§7.4）**：用户文档与 init 以 `dweb-cli test` 为默认；用例仍用
   `@dreamer/test`；`--unit` / path / filter 经 CLI 可稳定复现；`--verbose` 可见
   宿主命令；**发版后** JSR 用户与源码能力一致；L2 策略可选增强；**报告**（json
   / html / md，§7.4.10）落地后 CI 与 PR 可消费稳定产物。
