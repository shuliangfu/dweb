# dweb 依赖分析：优化与升级

> **结论先行**\
> dweb **3.5.11** 声明的 `@dreamer/*` 版本，与 monorepo
> **本地包版本几乎一一对齐**（唯一明显落后：**view 声明 `^2.0.5`，本地已是
> `2.1.0`**）。\
> 因此「依赖要不要全面优化」**不是**「把 caret 再抬一档」这么简单，而是三件事：\
> 1）**立刻对齐 view 2.1**（dweb 自身 + 下游 `render` 等传递依赖）；\
> 2）**依赖图底座统一**（各子包大量仍 pin
> `runtime-adapter@^1.0.x`、`test@^1.0.x`，应升到当前底座）；\
> 3）**按层做能力增强**：HTTP/渲染/构建/CLI/生产中间件优先，稳定内核小步走，可选包勿拖累主路径。\
> **不要**为「数字好看」无脑全仓 major；**要**建立「dweb 升级 ↔
> 子包协同发版」节奏。

| 项       | 值                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| 分析对象 | dweb `deno.json` / `package.json` 中的 `@dreamer/*` 依赖                                                                 |
| 对照基准 | monorepo 各包 `deno.json` **version**（2026-07-22）                                                                      |
| 文档性质 | **依赖矩阵 + 缺口 + 升级/优化优先级**（非 changelog）                                                                    |
| 相关     | [全面分析-优化与增强.md](./全面分析-优化与增强.md)、[CONSOLE应用架构规划.md](./CONSOLE应用架构规划.md)、`update-deps.sh` |

### 1.2 依赖分层（决策用）

```text
┌─────────────────────────────────────────────────────────────┐
│ L0  底座    runtime-adapter · i18n · service · utils        │
├─────────────────────────────────────────────────────────────┤
│ L1  内核    middleware · plugin · lifecycle · logger · config│
├─────────────────────────────────────────────────────────────┤
│ L2  HTTP    server · router · session · middlewares         │
├─────────────────────────────────────────────────────────────┤
│ L3  视图    view · render（+ 可选 preact/react npm）         │
├─────────────────────────────────────────────────────────────┤
│ L4  构建    esbuild（@dreamer/esbuild）                      │
├─────────────────────────────────────────────────────────────┤
│ L5  扩展    database · websocket · socket-io · plugins · image│
├─────────────────────────────────────────────────────────────┤
│ L6  产品面  console（CLI）· dweb 自身编排                     │
├─────────────────────────────────────────────────────────────┤
│ L7  开发    test（不进运行时发布图，但进 CI 稳定性）          │
└─────────────────────────────────────────────────────────────┘
```

**升级顺序原则**：先 L0 → L1 → L2/L3/L4，再 L5/L6；L7 可与 CI 修复并行。\
**原因**：上层 caret 对齐但下层仍 pin
旧底座时，**解析到的具体版本会分叉**，出现「本机一种、CI
一种、嵌套另一版本」的假绿。

## 2. 传递依赖健康度（比 dweb 声明更重要）

dweb 已声明 `runtime-adapter@^1.1.0`，但 **多数子包本地 `imports` 仍是 `^1.0.18`
/ `^1.0.19`**。\
在隔离安装（只装单包）或锁文件保守解析时，**不会自动吃到 1.1.0
的新能力**（错误码、子路径 `/fs` `/path`、Bun WS 升级修复等）。

| 子包（抽样）                                  | 本地 pin 的关键依赖                                              | 建议                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **render**                                    | `view@^2.0.2`、`runtime-adapter@^1.0.18`                         | **优先**：升 `view@^2.1.0`、`ra@^1.1.0`；评估 streaming / hydrate 适配  |
| **server**                                    | `ra@^1.0.19`、`esbuild@^1.1.9`、`router@^1.1.7`、`render@^1.1.7` | 升到与 monorepo 当前线一致（ra 1.1、esbuild 1.2、router/render 1.1.8+） |
| **router**                                    | `esbuild@^1.1.9`、`ra@^1.0.19`                                   | 跟 esbuild/ra 线                                                        |
| **middlewares**                               | `server@^1.0.8`、`logger@^1.0.0`                                 | **偏旧**；应跟当前 server/logger，避免类型/行为漂移                     |
| **console / config / database / session / …** | 普遍 `ra@^1.0.18`                                                | 批量 **^1.1.0**（小版本协同发 patch）                                   |
| **plugins**                                   | 依赖面宽（auth/queue/theme…）                                    | 随 dweb 插件场景回归；日志级别已优化                                    |
| **view 2.1.0**                                | 已 `ra@^1.1.0`、esbuild 1.2、server 1.1.9                        | 健康；**dweb 需跟上**                                                   |

### 2.1 重复与间接依赖

| 现象                              | 说明                                           | 建议                                                    |
| --------------------------------- | ---------------------------------------------- | ------------------------------------------------------- |
| dweb 直接依赖 vs 经 server 再依赖 | 正常编排层模式                                 | 保持 dweb 显式声明关键直接依赖，避免「透传黑洞」        |
| `@dreamer/image` 在 dweb imports  | **src 无引用**；esbuild/插件构建链可能间接需要 | 见 §5.4：要么文档化为 peer/可选，要么真正接线图片流水线 |

## 3. 逐包：现状、缺口、是否值得优化

### 3.1 必须动（P0）

#### `@dreamer/view`（2.0.5 → **2.1.0**）

| 维度         | 内容                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| 为何必须     | 2.1：子路径 `/csr` `/reactivity`…、`mismatchMode`、For LIS/安全 harden、`sideEffects: false`；dweb 全面分析已列为首项 |
| dweb 动作    | `deno.json` + `package.json` + examples/init 模板/`jsr-versions` → **`^2.1.0`**                                       |
| 协同包       | **render** 升 `view@^2.1.0` 并跑 view 引擎 SSR/Hybrid 测试                                                            |
| 风险         | esbuild 解析子路径；需 spike + 双跑 Deno/Bun                                                                          |
| 不做 Islands | 产品否决；依赖升级 **不包含** 岛屿能力接入                                                                            |

#### 底座批量对齐（P0 工程债）

| 动作                                                    | 范围                         | 产出                         |
| ------------------------------------------------------- | ---------------------------- | ---------------------------- |
| 各包 `runtime-adapter` → **`^1.1.0`**                   | 凡仍 `^1.0.x` 的 dweb 相关包 | 统一错误码/子路径/Bun WS     |
| 各包 dev `@dreamer/test` → **`^1.1.10`**                | 落后 `^1.0.x` / `^1.1.3` 等  | CI 钩子与浏览器稳定性一致    |
| **render / server / router / middlewares** imports 刷新 | 见 §2 表                     | patch 发版后 dweb 锁文件干净 |

> 底座对齐可 **多包 patch 批量发**（1.0.x → 声明 ^1.1.0），不必等 dweb
> 功能大版本。

dweb `imports` 另含：

| playwright                       | e2e        | 与 `@dreamer/test`、CI 镜像一致                      |

**原则**：引擎与 CSS 工具链 **以 render/esbuild 为源**，dweb
只声明「矩阵需要的上界」，避免三处各写各的。

## 5. 优化与升级路线图

### 5.1 浪潮 0 — 依赖卫生（数日，低风险）

| # | 项                                                                     | 负责人视角         |
| - | ---------------------------------------------------------------------- | ------------------ |
| 1 | dweb：`@dreamer/view` → **^2.1.0**（deno + package + 模板 + examples） | dweb               |
| 2 | render：`view@^2.1.0`、`ra@^1.1.0`，回归 SSR/Hybrid                    | render → dweb 锁   |
| 3 | 批量：相关包 `runtime-adapter@^1.1.0`、`test@^1.1.10`                  | monorepo 脚本/人工 |
| 4 | server/router/middlewares：imports 对齐当前线，必要时 **patch 发版**   | 各包               |
| 5 | 审计 `@dreamer/image` 是否可移出 dweb 直接依赖                         | dweb               |
| 6 | `./update-deps.sh` + Deno/Bun 全量测试；刷新 TEST_REPORT               | dweb               |

### 5.2 浪潮 1 — 与 dweb P0/P1 功能绑定

| # | 依赖侧                                   | dweb 侧收益                   |
| - | ---------------------------------------- | ----------------------------- |
| 1 | render：hydrate 选项 + 可选 stream       | Hybrid mismatchMode、流式 SSR |
| 2 | esbuild + dweb builder 契约              | CSR 可维护、包体              |
| 3 | middlewares：CSP/压缩文档与小增强        | 生产 profile                  |
| 4 | console：quiet/exitCode 等小 API（按需） | Console App `run`             |
| 5 | session/server 文档与多实例建议          | 生产可运维                    |

### 5.3 浪潮 2 — 中长期

| # | 项                                                      |
| - | ------------------------------------------------------- |
| 1 | database / plugins 与 Console、队列、定时任务边界产品化 |
| 2 | websocket/socket-io 压力与多实例指南                    |
| 3 | service/lifecycle 请求级作用域（若 App 拆分需要）       |
| 4 | view 3.0 兼容策略（**单独 RFC**，勿与本浪潮混发）       |

### 5.4 明确不该做的依赖动作

- 无收益的 **整仓 major** 或「版本号统一成同一个数字」。
- 在 dweb 里 **vendor** 复制 view/server 实现。
- 为 Islands 去升 render/view API。
- 把可选业务包（auth/payment/queue…）**默认塞进 dweb 硬依赖**（保持 plugins
  可选）。
- 只改 dweb caret、**不**升子包 imports → 锁文件/嵌套仍旧。

## 6. 协同发版策略（实操）

```text
建议顺序（示例：view 2.1 红利落地）

1. view 已发 2.1.0
2. render patch（升 view/ra + 适配测）→ 发版
3. server/router/esbuild 若仅 imports：可 patch 批量
4. middlewares 若升 server：patch
5. dweb 升 view（及需要的子包下限）→ 双引擎测试 → dweb 发版
6. 模板 jsr-versions / init 与 examples 同步
```

| 机制             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| caret `^`        | 允许兼容更新；**发版说明写清最低已测版本**                   |
| `update-deps.sh` | 根 + examples `deno update`；改完跑测试再锁                  |
| 兼容矩阵         | 在 dweb CHANGELOG / README 写：`view >= 2.1`、`ra >= 1.1` 等 |
| 回归门禁         | unit + integration + 抽样 e2e；Bun 与 Deno 都要              |
